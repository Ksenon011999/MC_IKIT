# Процесс командной работы

## 1. Соглашение о коммитах

Для сообщений коммитов используется формат Conventional Commits:

`<type>(#<issue-id>): <краткое описание>`

Основные типы коммитов:

- `feat` — добавление новой функциональности;
- `fix` — исправление ошибки;
- `docs` — изменение документации;
- `test` — добавление или изменение тестов;
- `refactor` — изменение кода без изменения поведения;
- `chore` — технические задачи и обслуживание проекта;
- `ci` — изменение конфигурации CI/CD.

В сообщении коммита указывается идентификатор задачи.

Примеры:

- `docs(#5): describe README structure`
- `docs(#5): add team process and review rules`
- `feat(#12): add health-check endpoint`

Сообщение должно кратко и понятно описывать выполненное изменение.

## 2. Правила работы с ветками

Основная долгосрочная ветка проекта — `main`.

Работа над задачами выполняется в отдельных короткоживущих ветках:

- `feature/<id>-...` — разработка функциональности;
- `docs/<id>-...` — работа с документацией;
- `chore/<id>-...` — технические задачи.

Название ветки должно содержать идентификатор задачи и краткое описание.

Пример: `docs/5-readme-structure`.

Прямые коммиты в `main` запрещены. Все изменения попадают в основную ветку через Pull Request.

## 3. Правила Pull Request и Code Review

Для объединения изменений создаётся Pull Request из рабочей ветки в `main`.

Автор Pull Request должен:

- указать связанную задачу;
- описать, что было изменено и зачем;
- написать, как проверить изменения локально;
- указать возможные риски;
- ответить на все замечания проверяющих;
- внести необходимые исправления.

Каждый участник команды должен проверить как минимум один Pull Request другого участника.

Ревьюер оценивает корректность изменений, соответствие требованиям задачи, читаемость кода и документации, а также наличие необходимых проверок.

Замечания должны быть конкретными и содержательными. Автор Pull Request обязан ответить на каждый комментарий и при необходимости исправить изменения.

## 4. Definition of Done для Pull Request

Pull Request считается готовым к объединению, если:

1. Указана ссылка на задачу через `Closes #номер`.
2. Описано, что изменено и почему.
3. Добавлена инструкция по локальной проверке.
4. Указаны возможные риски.
5. Получено не менее одного одобрения (Approve).
6. Все обязательные проверки CI завершились успешно.
7. На все замечания ревьюеров даны ответы.
8. Изменения соответствуют критериям приёмки задачи.

Объединение Pull Request выполняется после выполнения всех условий.

## 5. Общие правила команды

- Перед началом работы участник проверяет актуальность `main`.
- Для каждой задачи используется отдельная рабочая ветка.
- Изменения регулярно фиксируются небольшими логически завершёнными коммитами.
- Перед созданием Pull Request участник проверяет собственные изменения.
- Конфликты при слиянии разрешаются участниками, ответственными за соответствующие изменения.
- Все участники соблюдают единые правила именования веток, коммитов и Pull Request.
