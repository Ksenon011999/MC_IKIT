# Развертывание MC_IKIT

Локальные команды находятся в [README](../../README.md). Настройки Django
читают переменные из процесса. [Образец](../../.env.example) содержит имена переменных
и значения для локального окружения. Значения передаются через терминал или
менеджер сервиса.

| Переменная | Использование |
|---|---|
| `DJANGO_DEBUG` | `1` для локальной разработки. На сервере используется `0`. |
| `DJANGO_SECRET_KEY` | На сервере обязателен постоянный новый случайный ключ из менеджера секретов. При локальном запуске без значения ключ генерируется на процесс. |
| `DJANGO_ALLOWED_HOSTS` | Домены через запятую. При локальном запуске по умолчанию разрешены localhost и 127.0.0.1. |
| `DJANGO_DB_PATH` | Путь к SQLite. Для CI и сервера используйте отдельные файлы. |
| `DJANGO_EMAIL_HOST`, `DJANGO_EMAIL_PORT` | SMTP через SSL. По умолчанию используется порт 465. |
| `DJANGO_EMAIL_HOST_USER`, `DJANGO_EMAIL_HOST_PASSWORD`, `DJANGO_DEFAULT_FROM_EMAIL` | Данные сервисного почтового ящика и отправитель. При отсутствии реквизитов локальная почта выводится в консоль, серверная доставка отключена. |

В опубликованных настройках исходной ветки были ключ Django и пароль SMTP. Порядок
восстановления перед вводом в эксплуатацию: владелец ящика отзывает старый пароль и
создаёт новый, администратор стенда заменяет ключ Django, затем проверяет вход и почту.
Старому ключу не следует доверять при ротации. После замены действующим пользователям
потребуется повторный вход, прежние ссылки на сброс перестанут работать.

## CI и подготовка стенда

1. Проверка в pull request устанавливает зависимости, запускает Ruff, проверку Django,
   миграции на новой SQLite, `check --deploy` и тесты с покрытием.
2. Перед первым развертыванием архитектор подтверждает обновление исходных версий зависимостей и
   адрес/способ конфигурации HTTPS. Для обратного прокси отдельно проверяется передача признака
   HTTPS от доверенного прокси, чтобы приложение корректно определяло защищённые запросы.
3. На стенде выполните `python manage.py check --deploy`, сделайте резервную копию
   рабочей SQLite, запустите `python manage.py migrate --noinput` и
   `python manage.py collectstatic --noinput`. Запускайте `MCIKIT.wsgi:application`
   из каталога `MCIKIT` через production WSGI-сервер.
4. После запуска проверьте `GET /health` по HTTPS и восстановление пароля на
   тестовой учётной записи стенда. `/health` подтверждает доступность Django и не проверяет SQLite или SMTP.
5. При сбое восстановите предыдущий выпуск и совместимое состояние SQLite из резервной копии.

[Официальный чек-лист Django](https://docs.djangoproject.com/en/5.2/howto/deployment/checklist/).
