# Аутентификация MC_IKIT

| Компонент | Назначение |
|---|---|
| [Модель `users.User`](../../MCIKIT/users/models.py) | Наследует `AbstractUser`. Логин хранится в `username`, email применяется в восстановлении, а `role` хранит прикладные права `user`, `pro_user`, `super_user`. |
| [Маршруты приложения](../../MCIKIT/users/urls.py) и [корневые маршруты](../../MCIKIT/MCIKIT/urls.py) | Подключают формы регистрации, вход, выход и встроенные представления сброса пароля. |
| [Формы](../../MCIKIT/users/forms.py) и [представления](../../MCIKIT/users/views.py) | `RegisterUserForm` наследует `UserCreationForm`, `LoginUserForm` наследует `AuthenticationForm`; представления используют стандартную логику Django. |
| [Настройки Django](../../MCIKIT/MCIKIT/settings.py) | Настраивают пользовательскую модель, middleware сессии, аутентификации и CSRF, SQLite и отправку почты. |

## Поток запроса

1. Пользователь открывает `/users/register/` и отправляет HTML-форму. Форма проверяет
   занятость email, Django сохраняет хеш пароля через `set_password`, а представление
   после регистрации направляет пользователя на вход. Подтверждения email в этом потоке нет.
2. `GET /users/login/` отдаёт форму. В `POST` браузер передаёт `username`, `password` и
   CSRF-токен. `LoginUser` использует стандартный backend Django, сравнивающий пароль с
   хешем пользователя и проверяющий активность учётной записи.
3. При успехе Django записывает идентификатор пользователя и служебные данные аутентификации
   в серверную сессию. По умолчанию запись сессии хранится в таблице `django_session`
   в SQLite. Браузер получает cookie `sessionid` с идентификатором сессии. `LoginView`
   переходит на разрешённый `next`, а при его отсутствии на маршрут `main`.
4. При следующем запросе `SessionMiddleware` загружает сессию, а
   `AuthenticationMiddleware` восстанавливает `request.user`. Защищённые представления
   с `login_required` направляют гостя на настроенный вход. Роль и принадлежность к
   организаторам проверяются отдельно в коде приложения. Прикладная роль `super_user`
   отличается от флага Django `is_superuser` для Django admin.
5. `POST /users/logout/` использует `LogoutView` для очистки сессии и возвращает
   пользователя на стартовую страницу.

## Учетные данные и токены

- Пароль передаётся через POST формы и хранится как хеш с солью. Поле регистрации сейчас
  использует `TextInput` и одно поле пароля, поэтому работу валидаторов при регистрации
  стоит покрыть отдельным тестом. Форма входа использует `PasswordInput`.
- CSRF-токен защищает отправку форм. Аутентифицированное состояние представлено cookie
  `sessionid`. В рассмотренном потоке собственные JWT и refresh-токены отсутствуют.
- `POST /users/password-reset/` передаёт email. Для подходящей активной учётной записи
  Django отправляет ссылку с кодированным ID пользователя (`uidb64`) и подписанным
  токеном. Токен проверяется представлением `PasswordResetConfirmView`, по умолчанию
  действует три дня и становится недействительным после смены пароля.
  [Шаблон письма](../../MCIKIT/users/templates/users/password_reset_email.html).
- В серверном режиме cookie сессии и CSRF передаются с флагом `Secure`, включено
  перенаправление на HTTPS. Секреты SMTP и ключ подписи поступают из окружения.
  [Настройки развертывания](deployment.md).
