# Применение ИИ и риски

## Использование ИИ для тестов и документации

Codex подготовил сценарии для проверок развертывания по следующему запросу:

> Используй текущий маршрут health и класс Django SimpleTestCase. Добавь проверку JSON
> для GET и проверку метода POST. Для изменения LOGIN_URL добавь проверку параметра
> next при запросе гостя к профилю. Используй URL-имена из проекта и тестовые данные.

[Итоговый код проверок](../../MCIKIT/MCIKIT/test_health.py) вручную сверен с
`require_GET`, именами URL и ожидаемым поведением `login_required`. Локальный запуск
`python manage.py test MCIKIT.test_health -v 2` завершился успешно, 3 из 3.
Codex также подготовил [описание аутентификации](authentication.md) по маршрутам,
модели пользователя, формам и документации Django.

## Пример до и после верификации

Первая версия, предложенная ИИ, импортировала `get_random_secret_key` из
`django.utils.crypto`. Реальный запуск `manage.py check` обнаружил `ImportError`
в Django 5.1.6. В итоговой версии для локального временного ключа используется
`from secrets import token_urlsafe` и `token_urlsafe(48)`. Повторные проверки Django
и тесты прошли без ошибок.

| Риск | Мера |
|---|---|
| Неверный импорт или предположение о версии библиотеки | Сверять зависимости, запускать Django checks и тесты. |
| Прохождение поверхностных тестов при ошибке в бизнес-логике | Проверять сценарии на коде проекта, добавлять независимые позитивные и негативные проверки. |
| Раскрытие секретов и персональных данных | Передавать в запросы к ИИ только необходимый код без значений ключей, паролей, токенов, дампов и реальных учётных записей. |
| Ошибочный вывод о качестве всего проекта | Сопоставлять утверждения с логами и SHA, раздельно указывать результаты smoke-тестов и полного прогона. |
